# ADR 0005：Docker 优先的本地开发

- **状态：** 接受
- **日期：** 2026-08-12
- **决策者：** 项目所有者与 Codex

## 背景

项目会由人类与不同 AI 协作者长期接力，开发主机的 Node、npm、系统库和全局工具版本很容易漂移。项目所有者已运行 Docker Desktop，并希望尽量避免依赖安装和构建产物污染宿主机。

“完全不接触宿主机”并不现实：源代码、Git、浏览器、Docker Desktop 本身，以及 Blender 等图形工具仍可能运行在宿主机。需要的是一条明确、可复现的默认边界，而不是为了容器化牺牲开发体验。

## 决定

Web 应用的依赖安装、开发服务器、自动化测试和生产构建采用 **Docker 优先** 的本地入口：

- 仓库提供 `Dockerfile`、Compose 配置和 `.dockerignore`。
- Node 基础镜像使用明确版本；应用依赖由提交到仓库的 npm 锁文件固定。
- 默认文档不要求宿主机安装 Node 或 npm。
- `node_modules`、构建缓存和测试产物不得无意写入宿主机；优先使用镜像层或 Docker 命名卷。
- 应用进程默认以非 root 用户运行，使用 init 转发信号，并为开发服务提供健康检查。
- Docker 内的测试与构建命令应能被 CI 复用或等价重现。
- 凭据不写入镜像、Compose 文件或 Git；需要时通过已登记的环境变量或 secret 机制注入。

宿主机仍可负责：

- Git 与普通文件编辑。
- 浏览器人工验收及必要的浏览器自动化驱动。
- Docker Desktop 无法替代的 GPU、Blender 或其他图形化资产工作。
- 故障排查时的临时本机命令，但不得让它成为唯一可复现路径。

## 原因

- 新协作者不必先修复本机语言运行时，降低接手成本。
- 开发、测试和构建共享版本边界，减少“只在我的机器可用”。
- 依赖与产物和宿主机隔离，便于清理、重建与自动化。
- 保留浏览器和图形资产工具在宿主机运行的灵活性，避免过度容器化。

## 后果

### 正面

- 从全新检出到运行纵切只需 Docker Desktop 和文档化命令。
- Node 与依赖版本漂移更容易被发现和复现。
- AI 协作者可以用同一套命令执行验证。

### 代价与风险

- Windows/macOS 文件共享、端口映射和命名卷可能带来性能或权限差异。
- 第一次构建需要下载基础镜像和依赖，速度受网络影响。
- Docker Desktop 本身仍是宿主机依赖，并非零安装方案。
- WebGL/WebGPU 的真实体验必须在宿主浏览器中验收，容器测试不能替代它。

## 备选方案

- **直接使用宿主机 Node：** 启动简单，但会把运行时、依赖和缓存分散到每位协作者的机器上，暂不作为默认入口。
- **开发在宿主机、仅生产构建进容器：** 热更新可能更快，但无法达到项目所有者要求的宿主机最小污染。
- **所有工具都强制容器化：** 边界看似统一，但浏览器、GPU 和 Blender 的体验与复杂度不成比例，不采用。

## 后续验证

第一个工程节点应证明：

1. 宿主机没有 Node/npm 时仍能安装依赖并启动开发服务。
2. `node_modules` 不出现在宿主项目目录。
3. 容器内测试和生产构建通过。
4. 停止与清理命令明确，重新构建可以复现结果。
5. 普通目标浏览器能访问开发服务并呈现 Babylon.js 场景。

若热更新性能、文件权限或 GPU/浏览器联调持续阻碍开发，可通过新的 ADR 调整具体边界；不得只留下未记录的宿主机旁路。
